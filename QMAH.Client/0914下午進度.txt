● 分析完了，結論整理如下（依嚴重度排序）：

  1. 路由本身沒有衝突

  SocialController(api/v1/social/*)、SocialMediaController(api/v1/social/media/*
  )、SocialNotificationsController(api/v1/notifications)、以及藏在
  SocialEventsController.cs/SocialReportsController.cs 裡的
  AdminEventsController(api/v1/admin/events)、AdminReportsController(api/v1/admi
  n/reports)——五個路徑前綴互不重疊，也沒有兩個 controller
  做同一件事。沒有你擔心的「重複實作」問題。

  2. 真正的功能缺陷：活動審核通過後不會真的公開（bug，不是重複）

  - SocialController.GetEvents/GetEvent 只回傳 ReviewStatus=="APPROVED" && 
    PublishStatus=="PUBLISHED" 的活動。
  - 但現在唯一的審核端點 AdminEventsController.ReviewEvent（PUT 
    api/v1/admin/events/{id}/review）只更新了 ReviewStatus，完全沒碰
    PublishStatus。
  - 對照已棄用的 QMAH.Web/Areas/Social/Controllers/SocialEventAdminController.Re
    viewEvent，舊版有關鍵一行：item.PublishStatus = status == "APPROVED" ? 
    "PUBLISHED" : "DRAFT";——這行邏輯在搬到 API（commit f21d548）時被漏掉了。
  - 結果：現在用 API 審核活動「通過」之後，活動永遠不會出現在公開清單，因為 
    PublishStatus 卡死在 DRAFT。

  3. 死代碼：通知服務沒接上

  SocialNotificationService/INotificationService（namespace
  還用了跟其他檔案不同的 QMAH.Application.Services）完全沒有在 Program.cs
  註冊、也沒有任何 controller 呼叫它。實際上：
  - AdminEventsController.ReviewEvent 自己手動 new UserNotification{...} 塞進
    DbContext，繞過了這個 service。
  - AdminReportsController.ReviewReport 處理檢舉完全沒有發通知。

  4. 命名/慣例不一致

  SocialEventsController.cs（內容其實是
  AdminEventsController）、SocialReportsController.cs（內容其實是
  AdminReportsController）檔名跟類別名不符；這三個 admin/notification controller
  用 QMAH.API.*（大寫 API），跟專案其餘 controller 的 QMAH.Api.Controllers.V1
  風格不同，也沒繼承 ApiControllerBase（自己重新宣告 [ApiController]、自己手刻
  ClaimTypes.NameIdentifier 解析）。

  5. Angular 現有程式碼是對不上/打不通的

  - posts.ts 把 GET /api/v1/social/posts 回應直接當 Post[]
    用，但實際回傳是分頁包裝 ApiPage<SocialPostListItemDto>（多一層
    items），現在這支基本上抓不到資料。
  - admin-events.ts 打 GET 
    /api/v1/admin/events/pending——這個端點不存在，AdminEventsController 只有 PUT
    {id}/review，一定 404。
  - 更根本的問題：AuthService 目前純粹是前端 mock（假 signal、假
    token），從沒呼叫過 POST /api/v1/account/login 或 GET 
    /api/v1/account/antiforgery-token。所以任何需要登入 + X-XSRF-TOKEN
    的寫入端點（發文、留言、報名、檢舉）現在測都測不了。

  方案 A：接上共用 service
  - 在 Program.cs 註冊 AddScoped<INotificationService, 
    SocialNotificationService>()

  - 刪除 SocialNotificationService.cs，AdminEventsController 維持現在手動塞
    UserNotification 的寫法不變，AdminReportsController
    也維持現在「檢舉處理完不發通知」的行為不變

  測試流程：
  1. 確認本機 QMAH 資料庫已還原好（README 的步驟）

     proxy（proxy.conf.json）會把 /api 轉給 7249，這樣 cookie 才會落在 4200 這個
     origin，跟 Angular 的 withCredentials/XSRF 設定一致

  UI 接上 Angular 之前，有兩個選擇：
  - 快一點：直接用 https://localhost:7249/scalar 開 API 內建的 Scalar
    文件頁，對著 POST /api/v1/account/login（README 有列展示帳密，例如
    admin@qmah.local

  實際上比較乾淨的用法是二選一：

  選項 A（建議，最簡單）：整套都交給 VS Code
  - 用 VS Code 開 repo，按那個 compound launch，一次把 API + Angular 都啟動好
  - VS2026 這次就完全不用開來啟動任何東西
  - 這是目前唯一「兩個服務一次啟動、而且穩定會成功」的方式

  - VS2026 只負責啟動 QMAH.Api（選單選單一專案的「QMAH API」，不要選那個會拉
    Angular 進來、一直不穩的多專案 profile）
  - Angular 另外用一個純終端機（或 VS Code，但這時候 VS Code
    只是拿來開終端機，不用它的 compound launch）手動 npm start
  - 這樣 C# 程式碼的中斷點、IntelliSense 都還是在 VS2026 裡用，Angular
    就單純被晾在旁邊一直跑著

● 輸入正確帳密後會出現什麼畫面？

  老實說——幾乎沒有畫面變化。目前 dev-login.ts
  登入成功後，只會在左下角那個小面板裡顯示一行文字：「已登入：xxx@qmah.local」，
  僅此而已。畫面上其他地方（導覽列的「目前身份」徽章、側邊選單）完全不會跟著變，
  因為那些都是綁在右下角那個假的身分切換工具上，跟真正的登入完全是兩套獨立狀態。

  實際發生的事是在背景：瀏覽器會拿到真正的 ASP.NET Identity 登入
  cookie（.QMAH.Api.Auth）跟 XSRF
  token，之後你去發文、留言、報名活動、或（如果這個帳號本身是 Admin
  角色）打後台審核頁，這些 API 呼叫就會真的帶著登入身分過去，成功／失敗會照我們
  之前做的方式顯示（例如活動列表真的能載入、審核按鈕真的能按）。

  右下角「切換管理員/玩家身分」還能不能用？

  能執行，但完全是假的、沒有實際效果——我查過程式碼，它只會：
  1. 把 AuthService 裡一個本地的 signal 設成假資料（token: 'user-token'
     這種寫死的字串）
  2. 存進 localStorage
  3. 彈出一個 alert

  完全沒有打任何 
  API，不會影響你真正登入的身分，也不會真的取得或失去任何權限。它唯一產生的實際
  效果，是讓側邊選單「後台管理專區」那兩個連結變灰（[class.disabled]）——但那只是
  視覺樣式，不是真的路由守衛，就算變灰你點下去還是會進得去頁面，只是頁面裡的 API
  呼叫會因為你沒有真的用該身分登入而失敗。

  換句話說：現在有了真的登入小工具之後，這個假的切換面板已經沒有實際用途，留著反

  #1：重新登入的根本原因——Secure cookie 在 http/https 混用環境下不穩定

  QMAH.Api 固定跑 https://localhost:7249，但 QMAH.Client 的 Angular dev server
  預設是純 http://localhost:4200，中間隔著 proxy 轉送。原本 cookieSecurePolicy
  用 SameAsRequest——判斷依據是 Kestrel 收到的請求（永遠是
  https），不是瀏覽器實際感受到的 scheme（透過 proxy 其實是 http）。結果登入
  cookie（.QMAH.Api.Auth）跟 antiforgery cookie 都被標成
  Secure，在這種混合情境下能不能穩定留住要看瀏覽器怎麼處理，顯然在你的環境下不穩
  定，才會反覆掉登入狀態。

  修正：
  - QMAH.Api/Program.cs：開發環境的 cookieSecurePolicy 從 SameAsRequest 改成
    None
  - AccountController.GetAntiforgeryToken：手動設定的 XSRF-TOKEN-API cookie
    原本用 Secure = Request.IsHttps（同樣的問題），改成用環境判斷

  用 curl 實測驗證過：重啟 API 後，回應的 Set-Cookie 已經不再帶 secure;
  屬性了。正式環境（非 Development）完全不受影響，還是強制要求 HTTPS。

  #2：發文後要手動重整——其實是彈窗提早關閉蓋掉了錯誤訊息

  create_post_modal／create_event_modal 裡的送出按鈕包在 <form method="dialog">
  裡沒寫 type，瀏覽器預設當
  type="submit"，點下去的瞬間原生表單就會立刻把彈窗關掉，跟非同步的 API
  呼叫互不等待。如果那次請求剛好失敗（很可能就是 #1
  的登入問題），彈窗已經關了，你完全看不到任何錯誤提示，只能猜「是不是要重整」。

  修正：按鈕改成 type="button"，成功才用程式關閉彈窗，失敗時錯誤訊息會顯示在彈窗
  裡不會被蓋掉。posts.ts／events.ts 也一併補上了 401/一般錯誤的訊息區分。
