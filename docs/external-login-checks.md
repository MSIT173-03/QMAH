# 第三方登入與手動測試

所有環境採相同規則：優先依 Provider＋ProviderKey 查找綁定；首次使用且 Email 已有會員時新增綁定並沿用原會員。一般密碼會員須先驗證信箱，保留停權、鎖定與登入資格檢查，不需資料庫 migration。

目前未實作各第三方的信箱可信性檢查，也未提供原帳號重新驗證後的主動綁定流程，不能宣稱安全綁定補強已完成。

## 啟動

重新啟動 API，Angular 若已開啟通常會自動重新編譯。實際畫面若沒更新，重新整理登入頁。使用專用測試帳號，不要刪除目前展示帳號的綁定紀錄。

## 測試一：已綁定的第三方帳號

1. 登出 QMAH，再使用以前成功登入過、資料庫已有綁定的第三方身分登入。
2. 預期進入原會員中心，原有資料、點數仍是同一份。
3. 此項測試必須實際走第三方授權，單純修改網址不算完成登入測試。

## 測試二：首次同 Email

1. 重新啟動 API，不需設定環境或展示開關。
2. 以一般帳密登入你的展示會員，先確認已完成信箱驗證，再登出。
3. 分別使用回傳同一 Email 的 Google、Facebook、Microsoft 登入，每次測完先登出。
4. 預期每次都進入同一會員，暱稱、個人資料與點數一致；第一次使用的外部身分會新增綁定，已有綁定則沿用。
5. 如果第三方回傳不同 Email、沒有 Email 或供應者授權失敗，無法保證共用同一會員；需確認實際第三方帳號與連接器設定。

## 測試三：不符合登入資格

1. 使用尚未綁定第三方身分的測試帳號，以相同 Email 註冊一般帳號，但先不驗證信箱。
2. 第三方登入應顯示需要信箱驗證，不能新增綁定或登入。
3. 完成信箱驗證後重試，應沿用原會員。
4. 停權或鎖定會員不能新增綁定或登入。請使用專用測試會員確認，勿更動目前展示會員的狀態。

Google 的登入來源是 Google；Facebook 與 Microsoft 在本專題皆經 Logto。若兩種社群登入在 Logto 已整合成同一個 subject，QMAH 會視為既有同一綁定，不能用這種情況測試「首次未綁定」。請用獨立測試身分，勿為測試刪除展示會員資料。

## 測試四：真正的新會員

1. 使用 QMAH 尚未有對應 Email、也尚未綁定的第三方測試身分。
2. 預期沿用原本建立會員流程，再進會員中心。
3. 登出後再用同一身分登入，應回到相同會員。

這項需要真實資料庫及第三方設定，測試替身只確認無同 Email 衝突會進入建立流程，沒有代替實際註冊整合測試。

## 自動檢查

後端：`dotnet run --project tools/AccountVerificationChecks/AccountVerificationChecks.csproj`

前端：在 QMAH.Client 執行 `node node_modules/@angular/cli/bin/ng.js test --watch=false --include=src/app/features/auth/login/login.spec.ts`
