# 隔離壓測與本次改善

壓測只用來回答具體問題：公開參考資料是否一直重複查詢？突波會不會讓登入查核先壓垮資料庫？不測試已結束的 Azure 站，也不把本機結果當成正式環境容量。

## 執行

從根目錄執行：

```powershell
dotnet run --project tools/ApiVerification/ApiVerification.csproj -c Release -- --load --output api-load-results.json
```

工具自己建立臨時資料庫與只綁 loopback 的 Kestrel API，不接受外部測試網址，也不使用既有會員資料。背景寄信、AI、付款與訂單工作不會執行。執行後會關閉測試 host、刪除自己建立的合成資料，結果保存在指定 JSON。

Build 工作流程也可手動勾選 `run-load`，結果會寫入 job summary。這不會登入或重新部署 Azure。

## 改善內容

### 公開分類／年代

原本 metadata 與 catalog 控制器重複讀相同參考表。現在共用 `CatalogReferenceData`：

- 只保存公開分類及年代，保留各 API 原本的排序方式。
- 每個參考清單最長快取 30 秒，因此資料修改最晚可能要 30 秒才會顯示；重啟程序也會清除快取。
- 同時遇到冷快取時合併載入，不讓每個請求各自查詢。隔離 API 的 32 個冷啟動併發請求只產生 2 次 SELECT。
- 只有成功查詢才進快取，錯誤與取消不會變成永久保存的空資料。
- 不快取會員資料、登入狀態、點數、鑰匙、價格、訂單、付款或防偽 token。

### 過載與會員額度

將原本混在一起的門禁拆開，保留既有上限、區域隔離、有限佇列與等待逾時：

1. CORS 先包住錯誤回應，讓允許的前台能讀取 429／503。
2. 啟用部署穩定限制時，`QmahRequestAdmission` 在認證之前取得名額，避免超量請求先進入 Identity 的資料庫查核。
3. 建立登入身分後才執行 auth／verificationEmail／socialContent 的端點限流，社群額度才能按會員分配。
4. 授權與防偽檢查通過後才執行控制器。拒絕回應帶 Retry-After，前端可依原本的讀取重試規則處理；寫入不自動重送。

隔離情境會故意暫停兩個已獲准請求的認證 SELECT，再送超量請求；確認它在另一個認證 SELECT 開始前收到 429。釋放原請求後，管理 API 仍回正常的 403，公開 API 又可回 200，不需要重啟服務。

metadata 歸在 catalog 區，不和帳號查核競爭同一份區域名額；測試也驗證帳號區忙碌時，已暖機的公開資料仍可讀取。

這組情境驗證的是有限並行、拒絕位置與恢復行為，不是資料庫長時間負載能力。穩定限制仍由 `Hosting:StabilityLimitsEnabled` 明確開啟；本機 Development／Docker 展示預設沒有自動套用雲端限制。

## 何時再測

改到快取、查詢、登入查核或限流順序時重跑同一情境，保留 JSON，比較查詢數、成功／拒絕數與延遲分位數。只有具體疑慮才擴充情境；真實 SQL Server 的索引、寫入競爭或長跑測試，需要另外準備隔離資料庫與目標，不直接拿正式站試。
