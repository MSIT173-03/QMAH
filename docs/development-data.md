# 共同資料與開發測試資料

QMAH 只有一份共同資料庫設計。每位開發成員在本機 LocalDB 使用獨立副本，共用相同 Schema 與基準資料，CRUD 測試互不影響。

## 開發時怎麼拿資料

先從 GitHub Release 還原最新 `QMAH-reference-*.bak`。參考資料庫包含 Schema、256 件文物、256 筆題庫設定、256 件對應商品，以及列表、詳細頁與關聯查詢所需的情境資料。

還原後可在本機 LocalDB 新增、修改與刪除測試資料。各副本的資料列不需要完全相同；共同契約是 Schema。

按 F5 不會自動建表、不會自動塞資料，也不會覆寫本機資料。

## 目前參考資料庫已有什麼

以下內容已在目前的 `QMAH` 參考資料庫逐表確認。除了 Identity 的 Claim、外部登入與 Token 這三張標準表刻意維持空白外，業務資料表都有可查詢的起始資料。

這不是要把所有畫面狀態都預先塞滿。它的用途是讓每個 Area 第一次做列表、詳情、關聯查詢或寫入時，有一組可直接使用的起點；空資料、錯誤輸入、不同狀態與大量資料，仍應在自己的 LocalDB 補測。

| 範圍 | 已有資料 |
| --- | --- |
| Catalog | 8 個分類、13 個年代桶、256 件文物，以及鑰匙定義、餘額、流水、解鎖各 1 筆情境資料 |
| Game | 256 筆題庫設定、2 個房間、3 位玩家、1 個回合、2 筆作答與 1 筆投票 |
| Social | 49 筆貼文、49 筆留言，另有檢舉、公告、活動、報名與通知情境資料 |
| Store | 256 件商品、1 筆購物車、1 組優惠券情境資料、3 筆訂單、付款與成交明細 |
| User | 8 個 Identity 帳號、2 個角色、8 筆 Profile，以及地址、成就、會員成就各 1 筆情境資料；標準 Identity 的 Claim、外部登入與 Token 目前為空白 |

這些資料只用來讓畫面和關聯有東西可看。社群資料刻意準備數十筆，方便檢查清單、排序、狀態與分頁；要測試新增、編輯、刪除、空資料或錯誤流程時，直接在自己的 LocalDB 建立需要的資料即可。

訂單、付款、房間、活動與檢舉的資料只提供代表性情境，並非每一個狀態值各一筆。若畫面需要測試 `CANCELLED`、`FAILED`、`PENDING_PAYMENT` 等特定狀態，就在自己的資料庫建立；不要為了測畫面而改共同基準。

## 哪些資料是共同基準

| 資料 | 用途 | 變更方式 |
| --- | --- | --- |
| `catalog.Artifacts` | 圖鑑使用的文物、圖片、來源、年代與尺寸 | 透過資料處理工具更新，不能各 Area 任意改成自己的版本 |
| `game.ArtifactQuestionEntries` | 每件文物是否可出題、題型與難度 | 與文物共同基準一起驗證 |
| `store.Products` | 對應文物的商城商品 | 工具產生初始商品資料；商城可在功能內維護自己的名稱、售價、庫存與上架狀態 |
| `user.AspNet*` | Identity 的帳號、角色與登入資料 | 一律用 Identity API 操作，不直接寫資料表 |

圖鑑、題庫與商城用同一個 `ArtifactId` 對應。三邊共用已授權的 Open Data 文物圖片；商城另外保存自己的名稱、說明、尺寸、售價、庫存與上架狀態。

## 哪些資料可以自行建立

下列都是各 Area 開發時可以直接在自己資料庫建立的測試資料：

- Game：房間、玩家、回合、作答、投票
- Social：貼文、留言、公告、活動、報名、通知、檢舉
- Store：購物車、折價券、訂單、付款、點數
- User：Profile、地址、通知、成就
- Catalog：分類管理頁需要的測試分類、鑰匙、解鎖紀錄

測試資料必須符合既有外鍵、唯一索引與 CHECK constraint。資料列可依開發情境調整；資料表結構則依共同 Schema 變更流程處理。

若資料庫是從既有正式文物資料開始、但還沒有社群展示資料，可執行 [`database/seed-showcase-data.sql`](../database/seed-showcase-data.sql)。這份腳本只新增貼文與留言，不會改動 Schema，也不會由網站啟動流程自動執行。

## 訂單與付款目前的規則

一張訂單只對應一筆付款紀錄，`Payments.OrderId` 有唯一限制。付款失敗或取消時，訂單改成 `CANCELLED`；使用者要再買一次，就建立新的訂單與新的付款紀錄。

這個規則讓訂單、付款與後台列表比較好理解，也符合目前專題不需要處理多次付款重試的範圍。

## 資料庫結構什麼時候要提出

下列變更需先提交資料庫結構變更說明：

- 新增、刪除或改名資料表、欄位
- 改資料型別、可否為 `NULL`、預設值、CHECK constraint
- 新增或修改外鍵、唯一索引、一般索引
- 改變跨 Area 的資料關係或歷史資料保存方式

只是在自己的 LocalDB 多建幾筆商品、訂單、貼文或會員資料，不需要提出。

## 資料存取的共同規則

```text
單表 CRUD：Controller → QmahDbContext → SQL Server
跨表交易、長流程、外部服務、重複呼叫或獨立測試：Controller → Service → QmahDbContext → SQL Server
登入與角色：Controller → Identity API → SQL Server
```

不採「每張表一個 Wrapper」、Generic Repository 或「每張表一個 Service」。只有外層確實需要保護不可繞過的行為或轉接不能修改的第三方物件時，才建立特定 Wrapper；一般 EF Core CRUD 不需要。

逐表筆數與狀態分布見[參考資料庫內容](database-content.md)。完整寫法見[QmahDbContext 使用手冊](dbcontext-usage.md)與[後台開發起點](backend-start-guide.md)。

## 更新共同基準時的流程

```text
資料工具整理與驗證
  → SQL Server 共同資料庫
  → Entity、QmahDbContext、Schema.sql 一致性檢查
  → 輸出新的參考 .bak
```

工具輸出的原始檔、快取與品質報告只放在工作區 `_工具輸出`。Repository 只保存網站需要的程式、圖片與文件。
